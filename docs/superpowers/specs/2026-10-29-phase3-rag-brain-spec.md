Status: v2 DRAFT — supersedes the v1 draft after principal review (15 findings, 7 Must) + assumption verification (research/phase3-brain-assumption-verification-2026-10-29.md, all sources fetched 2026-10-29). Awaiting owner approval before publishing to tracker. Per master plan `docs/superpowers/plans/2026-10-25-platform-own30-master.md` Phase 3; design basis `research/python-rag-audit-2026-10-17.md` (§2.3, §3) with explicitly-marked supersessions.

## Problem Statement

The script writers (documentary + Shorts) start from zero memory every run: they don't know which of the owner's past videos performed well, what topics were already covered, or which hooks/structures were used across the 15-channel network. YouTube's inauthentic-content policy (renamed Oct 2025) demonetizes templated/repetitive output, and the only anti-repetition defense today is human memory. Meanwhile the system's most valuable asset — past scripts plus their performance data — sits unused in state files. The owner's channels need scripts that improve over time and can PROVE they don't repeat.

## Solution

A **memory brain**: every published AI-generated script, its performance numbers, and the research corpus are embedded into a vector index (Neon pgvector — already in the owner's database). Before writing, the renderer asks the brain for the most similar past videos + their stats, and writes with that context. After writing, the brain checks the new script's **semantic similarity** to past scripts — too similar = BLOCKED, the writer retries (escalation semantics defined precisely in D5). Everything runs **inside CI/cloud jobs** — zero dependency on any personal machine (owner requirement, 2026-10-29).

## User Stories

1. As the owner, I want the writer to see my most similar past videos and their performance before writing, so that new scripts reuse what worked and avoid what didn't.
2. As the owner, I want near-duplicate scripts blocked automatically, so that no channel publishes content that risks the inauthentic-content policy.
3. As the owner, I want cross-channel repetition *warned* (and blocked only where a template marks it blocking), so that my 15 channels can't quietly converge without me seeing it.
4. As the owner, I want the memory to include the research corpus, so that scripts cite the documented sources instead of generic claims.
5. As the owner, I want a similarity score recorded for every published script, so that I can PROVE variation if YouTube ever reviews a channel.
6. As the owner, I want the whole memory system to run in CI/cloud, so that shutting my laptop for a month changes nothing.
7. As the owner, I want failed memory lookups to degrade to today's behavior (write without memory) with a visible warning, so that the system never goes dark because the brain is down — except finance-gated templates, where an unreachable dedupe gate blocks rather than risks a policy-violating publish.
8. As the owner, I want the variation threshold configurable per template, so that strict finance templates can be tighter than loose quote channels.
9. As the owner, I want the memory index to rebuild idempotently, so that re-running the indexer never duplicates vectors or loses refreshed performance data.
10. As the owner, I want the brain's cost to be ~zero (local embeddings in CI, no embedding API), so that memory scales with the network for free.

## Implementation Decisions

- **D1 — No framework; ONNX runtime, not torch.** Plain Python + Neon pgvector (research decision 2026-10-17, reaffirmed). Embeddings via **`fastembed` 0.9.1** (Qdrant, Apache-2.0) — chosen over `sentence-transformers` after verification (research/phase3-brain-assumption-verification-2026-10-29.md): ONNX Runtime avoids the ~539MB CUDA-torch wheel on CI (CPU-only pin otherwise required), 512-token context, higher MTEB retrieval score (62.17 vs ~56.26 for MiniLM), same 384 dims. One small FastAPI app (`services/ai/app.py`): `/health`, `/context`, `/dedupe`, `/embed`. One pinned `requirements.txt` (fastapi 0.162.0, uvicorn 0.54.0, fastembed 0.9.1 — versions verified 2026-10-29; fixes the repo-wide unpinned-Python problem).
- **D2 — Embedding model + THE CHUNKING DECISION (supersedes v1 D2/D4; resolves review R-7 + verifier CRITICAL).** `all-MiniLM-L6-v2` (served BY fastembed) truncates at 256 word pieces ≈ 190 words — a 1,300-word documentary script loses ~87% of its text if embedded whole. **Therefore: scripts are embedded as CHUNKED SUB-VECTORS (~200-token windows, per master plan §4's original "one vector per scene" decision, dropped in the v1 draft, re-adopted)**: documentary = one vector per chapter + one pooled whole-doc vector; Shorts = hook vector + points vector + pooled. `/dedupe` compares **max chunk similarity** (not pooled-vs-pooled) — a single matching scene is a match even if the rest differs. 384 dims verified; model upgrade path in AC-P3-14.
- **D3 — Storage: Neon pgvector.** Table `script_memory` (id bigserial, channel_id, script_kind, chunk_kind (scene|hook|points|pooled|corpus|research), job_id, created_at, content_hash UNIQUE per (chunk_kind, hash), embedding vector(384), performance jsonb, meta jsonb, model_id text, model_dim int). **Exact-scan retrieval — no ivfflat/hnsw index mandated** (pgvector README: exact = perfect recall; correct at the owner's ~1k-10k-vector scale; revisit at ~50k). Idempotency: hash-keyed upsert per AC-P3-13.
- **D4 — Corpus selection (resolves review R-8):** embed **published AI-generated scripts only** — named sources: `explainer/public/lf-*.json` (docs), `yt-mcp/state/<slug>.json` (titleHistory/lastVideos Shorts), `fb-outbox/<slug>/*.json`. **Excluded:** `source:'fallback'` template scripts, gate-rejected scripts (`gateRejected`), failed-run outputs (embedding the canned fallback would make every future AI script "similar" to it). Plus the research corpus (glob `research/*.md` — 86 docs today and growing; never hardcode a count) and template beat examples. Performance data source: `reporting/logs/posts-log.json` + `state/report-stats.json`; richer refresh joins Phase 4's analytics snapshots.
- **D5 — Write-time flow (corrected walk model, resolves review R-4/R-5).** The escalation walk loop lives INSIDE `callScriptBrain` (youtube-engine.mjs:477-493), not in the callers — deepdive calls `callScriptBrain` exactly once (yt-deepdive.mjs:230). Therefore: `/context` is queried at prompt-assembly (engine ~510-538; deepdive LONG_PROMPT call at :230); `/dedupe` is wired as a **new injected hook** in `callScriptBrain` (e.g. `checkDup(parsed) => {blocked, topMatchId, score}`), inserted between shape validation (youtube-engine.mjs:488) and return (:489). A BLOCKED verdict bypasses `SHAPE_RETRY_CLASSES` (parse_error/empty_response only) as a THIRD re-walk reason, and walks 2+ append guidance **naming the top match** ("your previous video 'X' covered this — vary the hook and examples"), or walks 2-3 would reproduce the same near-duplicate. **Exhausted-walks terminal (new, resolves the AC-P3-4/5 contradiction):** all walks BLOCKED → Shorts: `source:'fallback'` terminal → slot skipped at yt-daily.mjs:244 (fail-closed, no publish); doc: `llmScript` throws → nonzero exit → episode retried next doc day. Brain-unreachable → never halts (AC-P3-5).
- **D6 — Failure policy (explicit supersession, resolves review R-3):** **Supersedes master plan §4 and the v1 draft:** brain/pgvector/embedding UNREACHABLE → fail-open everywhere with one warning (never dark — AC-P3-5). Brain UP and dedupe verdict BLOCK → **fail-closed for templates whose registry meta has `review_required` containing the channel's niche class (finance today), fail-open-with-WARN-verdict otherwise** (recorded, per AC-P3-16). The registry already encodes this tiering via `review_required`.
- **D7 — CI-only runtime (owner requirement AC-P3-6; CI realities per verifier R-11):** sidecar spawned inside CI jobs (localhost) exactly like existing Python steps; CPU-only wheels (fastembed = ONNX, no torch); model cache via `actions/cache@v6` on the fastembed cache dir with a cold-start fallback that fail-opens per D6; one-time backfill + re-index = workflow_dispatch jobs; zero personal-machine steps.
- **D8 — Thresholds from the registry (rewritten per review R-1):** NEW registry meta field `variation_threshold` (number, default 0.85 cosine, validated by preflight like other meta) + `cross_channel_threshold` (default threshold + 0.05). Template identity is threaded into the dedupe call via the pipeline (slug → template id → registry meta); legacy/unassigned channels use the 0.85 default. Thresholds are DATA — no code edit to tune.
- **D9 — Node↔Python HTTP contract pinned (resolves review R-12):** JSON schemas for /context (in: channel, kind, topic, k; out: [{id, score, performance, excerpt}]), /dedupe (in: channel, kind, template_id, chunks[], threshold; out: {verdict, score, top_match_id, neighbors[]}), /embed, /health — pinned as shared schema files referenced by both sides. **Similarity convention pinned: vectors stored normalized; pgvector `<=>` returns DISTANCE = 1 − cosine similarity; the gate is `similarity ≥ threshold` blocks.** An implementer flipping this silently would invert the gate — the schema comment + a unit test pin it.
- **D10 — Dropped audit decisions, explicitly marked (resolves review R-13):** Anthropic contextual-retrieval prefixes, hybrid tsvector/RRF retrieval, and Ragas eval — NOT in Phase 3 (the last replaced by the paraphrase-fixture quality eval, AC-P3-Q). Exact-scan retrieval, no ANN index at ~1k-10k vectors (revisit ~50k). Embedding model supersedes the audit's paid `text-embedding-3-small` (zero-cost requirement; the audit's re-embed warning carried into AC-P3-14).

## Acceptance Criteria (EARS-style)

- AC-P3-1: When the indexer runs against an unchanged corpus, it shall insert zero rows; when the corpus or performance data has changed, it shall insert new hashes and update existing rows' performance/meta in place (no duplicate row, no re-embed of unchanged content).
- AC-P3-2: When a generator writes a script in CI, the same job shall embed its chunks into the memory (write-time embedding, cloud-side — no personal machine involved).
- AC-P3-3: When a generator starts writing, it shall query `/context` and record the retrieved past-script ids + performance in the job output (provenance).
- AC-P3-4: When a new script's max chunk similarity to a past script of the SAME channel exceeds the template's `variation_threshold`, the system shall BLOCK (consume the escalation retry), and on exhausted walks shall fail the script phase using the lane's existing terminal (Shorts: slot skipped via the `source:'fallback'` gate; doc: nonzero exit, episode retried next doc day), recording a terminal BLOCKED verdict with the final top match id and score.
- AC-P3-5: When the brain, pgvector, or embedding model is unreachable, the system shall proceed without memory (fail-open), log one warning naming the failure class, and fire one ntfy alert — generation never halts for memory-availability reasons (distict from AC-P3-4's brain-up-policy-block).
- AC-P3-6: When any memory operation runs (index, embed, query, migrate, backfill), it shall execute inside CI/cloud jobs using only requirements.txt + repository files + environment variables — zero steps on a personal machine.
- AC-P3-7: When `/dedupe` evaluates a script for a channel with an active template assignment, the threshold shall come from that template's registry `variation_threshold` field; for legacy/unassigned channels it shall use the 0.85 default.
- AC-P3-8: When retrieval returns exemplars, the system shall attach their performance data (views/retention where available) so the writer can weight what worked.
- AC-P3-9: When the research corpus is queried, results shall be usable as citation sources (path + doc id recorded in the script's provenance).
- AC-P3-10: When the sidecar receives `/health`, it shall report model-loaded + pgvector-reachable states for CI preflight checks.
- AC-P3-11: (exhausted-walks terminal — folded into AC-P3-4.)
- AC-P3-12: When `/dedupe` returns any verdict (PASS, WARN, or BLOCK), the system shall write one row to a Neon `dedupe_verdicts` table (channel_id, script_kind, job_id, verdict, top_match_id, score, threshold, created_at); a failed write shall degrade to one log warning and never halt generation. This table doubles as the variation-evidence ledger for YouTube reviews.
- AC-P3-13: When the indexer encounters an existing content_hash, the system shall update that row's performance and meta in place (no duplicate row, no re-embed); it shall insert rows only for new hashes and embed only when the hash or model stamp is new.
- AC-P3-14: When the pinned embedding model id or dimension changes, the system shall re-embed the entire corpus into the new dimension before any /dedupe query runs, and /dedupe shall fail open with a warning when it detects rows whose model stamp differs from the current model.
- AC-P3-15: When the indexer selects scripts to embed, the system shall include only published AI-generated scripts and shall exclude fallback-template scripts, gate-rejected scripts, and scripts from failed runs.
- AC-P3-16: When a new script's max similarity to a DIFFERENT channel's same-template script exceeds the cross-channel band (template threshold + 0.05 unless registry-specified), the system shall record a WARN verdict with the match id — it shall not BLOCK unless the template's registry meta marks cross-channel convergence as blocking.
