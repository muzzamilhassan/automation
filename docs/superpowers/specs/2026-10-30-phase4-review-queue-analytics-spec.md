## Problem Statement

Six things hurt today:

1. **Duplicate uploads are one crash away.** YouTube's `videos.insert` has no idempotency key (platform-youtube-api-oauth research row 3): if a job dies between YouTube accepting the upload and the state file being written, the video exists but the system doesn't know it — the next run can make it again. This already happened: the old cron caused 8 duplicate longform uploads; "First $10,000" published 4×, "Stop Begging For Respect" 3× (`research/project-full-audit-2026-10-09.md` §2.3). Today's defenses are title-fuzzy gates (`lib/dup-gate.mjs`) and an artifactId ledger for the weekly longform lane — neither survives that crash.
2. **A run has no memory of itself.** `channel-pipeline.mjs` runs each step as a child process and keeps no structured record — the code says so itself (line 160: "the pipeline keeps no structured run record of its own"). A job killed mid-render restarts from zero next day, re-spending research + script + TTS money on steps that already succeeded.
3. **Warnings are lost in push notifications.** Everything alarming — dead tokens, quota gate, failed verification, blocked preflight — is an ntfy push (`lib/ntfy-alert.mjs`, plus inline fetches in `channel-pipeline.mjs`). If you miss the phone notification, the event never existed. The policy research (`research/platform-youtube-policy-compliance-2026-10-24.md` §4) defines a 5-severity ladder and a hard-block list; nothing implements it.
4. **Nothing a human reviews before upload.** Scripts go research → generate → render → upload with no person in the loop. Finance templates already declare `review_required: ['finance']` (`studio/lib/template-registry.data.js`) and Phase 3 enforces a fail-closed dedupe gate for them — but there is no place to actually READ a script, see its claims against its sources, or answer a disclosure checklist. The script JSON doesn't even carry sources/claims today (`youtube-engine.mjs:829` returns hook/points/closing only).
5. **No analytics loop.** `/api/analytics` (`studio/app/api/analytics/route.js`) pulls a live 28-day window with a 1-hour cache and stores nothing; the Daily Excel (`daily-excel-report.mjs`) lands in git (`state/report-stats.json`, `logs/posts-log.json`). Snapshots are never persisted, so there is no channel leaderboard, no template/topic win rates, and no data for the Phase 6 keep/kill review.
6. **Session revocation is close but not complete.** The opaque `sessions` table with instant revocation already exists (`studio/lib/session-db.js`, the Oct-09 A1 hardening) — but only self-service: a user can sign out their own devices. The owner cannot revoke someone else's session from the admin panel.

## Solution

Six slices. Each gets one paragraph here, decisions (D) and acceptance criteria (AC) below.

**S1 — State machine + artifact store.** Every channel run becomes a recorded job with one row per step (research, script, TTS, render, upload, verify…), and every file a step produces is indexed by a fingerprint of its contents — like a library where each book is shelved under its own fingerprint, so a finished step is provably finished and never redone. The bytes that resume and approval DEPEND on (script payloads, TTS audio, review-gated renders, thumbnail candidates) are persisted to scoped Vercel Blob storage; everything else stays where it lives today. A killed job re-enters at the failed step instead of starting over — but only when the earlier steps' bytes are actually retrievable, never on an index entry alone.

**S2 — Upload intent + orphan reconciliation.** Before touching YouTube, every upload writes a note: "I am about to upload X for channel C, slot date D, slot N." The resumable upload's session URI — the parking ticket for a half-finished upload — is saved on that note as a secret. If a run dies after YouTube accepted the video but before the system recorded it, the next run finds the note, checks YouTube, and claims the existing video instead of uploading again. A nightly diff of playlist vs. ledger catches anything that slips through. This kills the duplicate-upload class at the root.

**S3 — Warnings table + dashboard.** Every alert the pipeline fires today also lands in a Neon `warnings` table with the policy research's 5 severities, the verbatim official quote + link, the evidence, and a last-checked date. A new Studio page lists open warnings per channel, with acknowledge, "re-check now", and owner manual-resolve. The policy file's hard-block list (verified technical constraints only) makes the pipeline PARK a channel: an open Blocking warning (e.g. revoked token) skips that channel's production runs — but parked runs still execute cheap health probes, and a nightly probe job re-tests parked channels, so parking can never become a deadlock. ntfy stays as the push channel — the dashboard is the durable record.

**S4 — Review queue.** Scripts gain a structured record: full text, `sources[]`, `claims[]` (which claim cites which source), and disclosure flags. A new Studio page shows script and sources side-by-side with claim↔source links, a flagged-claims panel, and the Phase 3 dedupe verdict. Where the channel's assigned template declares a review class (finance today; medical and disclosure added), the pipeline is fail-closed — including when the gate's own state is unreadable — and approval dispatches the resume run automatically. Thumbnails produce 3 candidates at render; the upload proceeds with candidate 1 and the owner can swap the thumbnail any time before the video goes public.

**S5 — Analytics ingestion.** A nightly GitHub Actions job writes `analytics_snapshots` rows (Data API `videos.batchGetStats` + Analytics API reports over a trailing 4-day window) — the same scopes the live `/api/analytics` panel already uses, probed per channel with a re-auth checklist where a scope is missing. Studio grows a channel leaderboard and template/topic win rates computed from snapshots, every view stamped "data through \<date\>" because Analytics numbers settle 48–72 hours late.

**S6 — Roles hardening (shrunk — owner-confirmed, OQ-1).** The sessions table exists. What's added: an owner-only view of ALL active sessions with per-session revoke (instant sign-out for any device), and cleanup of expired rows. Client role stays dormant.

## User Stories

1. As the owner, when a render job is killed mid-run, I want to re-run it and have it resume at the render step, so I never pay twice for research/script/TTS that already succeeded.
2. As the owner, I want every upload pre-recorded as an intent and reconciled against the channel's uploads playlist, so a crash can never again publish the same video twice.
3. As the owner, I want every alert stored in one dashboard with severity and the official policy quote, so a warning I missed on my phone still exists when I open the laptop.
4. As the owner, I want a channel with a revoked token automatically parked with a Blocking warning AND still probed for recovery, so a dead channel can't burn quota while parked forever — and comes back the moment the token is fixed.
5. As the owner, I want to read a finance/medical script next to its sources before it can upload, so a fabricated or unsourced claim never reaches my channel under my name.
6. As the owner, I want the AI-disclosure checklist presented in YouTube's official wording before I approve a script with realistic synthetic visuals, so the upload sets disclosure flags correctly the first time.
7. As the owner, I want 3 thumbnail candidates per video the admin panel configures for picking, swappable any time before the video goes public, so thumbnails stop being take-it-or-leave-it without slowing the daily queue.
8. As the owner, I want a nightly snapshot of every channel's numbers and a leaderboard, so I can see at a glance which channels earn their render minutes (the Phase 6 keep/kill decision).
9. As the owner, I want per-template and per-topic win rates, so catalog decisions in Phase 5 come from data, not vibes.
10. As staff, I want to see the warnings dashboard and prepare script reviews, so day-to-day monitoring doesn't wait on the owner — while fail-closed approvals stay owner-only (owner-confirmed, OQ-5).
11. As the owner, I want to revoke any team member's session from the admin panel the moment they leave, so access ends in seconds, not in 30 days.
12. (Dormant) The client role gains nothing in Phase 4 — no SaaS work (scope pivot: own-portfolio-30).

## Implementation Decisions

### S1 — State machine + artifact store

- **D1 — Three NEW Neon tables: `jobs`, `job_steps`, `job_artifacts`.** `jobs`: id, channel_id, kind (shorts|doc|clips|pipeline), trigger (cron|dispatch|resume|studio), status (running|succeeded|failed|partial), resumed_from_job_id, started/finished_at. `job_steps`: job_id, step name, seq, status (pending|running|succeeded|failed|skipped), error class, started/finished_at. `job_artifacts`: job_id, step, content_hash (sha256 of bytes), kind (render|thumb|audio|doc-episode|script-payload), location pointer (blob key | github-release | workspace-ephemeral). Schema ensured idempotent at first write, same pattern as `usage_events` (`lib/ai-adapter.mjs:355` `makeUsageWriter` — the existing "ensure-schema-on-write" house pattern). The job id flows into `usage_events.job_id` (already a TEXT column — `lib/ai-adapter.mjs:388`) so cost rows join to runs. Writer: NEW `lib/job-store.mjs` (repo-root lib, Node, callable from the pipeline and from child scripts). **Divergence flagged (as OQ-1 was):** the master plan §2 names `job_events`; v3 builds `job_artifacts` instead — a per-step append-only event log adds write volume without a Phase 4 reader, and the artifact index is what resume and review actually query. If the owner wants the event log too it is an additive table later. **Hash disambiguation (one line):** the artifact hash fingerprints FILE BYTES; the Phase 3 canonical hash (`youtube-engine.mjs` brain path) fingerprints normalized SCRIPT TEXT — two different fingerprints for two different jobs, never compared.
- **D2 — Instrumentation point is `channel-pipeline.mjs`, not the workflows.** The pipeline already defines the step list (preflight → shorts → brain-embed → verify → episode → staging) and the independence semantics ("each step is independent: if one fails, the rest continue", line 6). Steps register with the job store; exit semantics pinned precisely: **end-of-run exit 0 with per-step outcomes recorded (today's line 359 behavior); unknown slug and preflight-block exit 1** (today's lines 26/157 behavior). Steps disabled by config — the `PLATFORMS_PAUSED` FB/poster lanes (lines 231, 253) — are recorded as `skipped`, so the step vocabulary is stable whether or not platforms are paused. Child scripts (yt-daily, yt-deepdive) report sub-steps where cheap (script, tts, render inside yt-daily) — best-effort, never fatal.
- **D3 — Artifact INDEX for everything; scoped Vercel Blob for resume/approval-critical bytes (OQ-2 as scoped by review).** Renders already get archived to GitHub Release assets (`yt-daily.mjs:319` `archiveUpload`); intermediates live in the ephemeral GHA workspace and `fb-outbox/`. **Blob persists ONLY the four byte classes that resume or approval depends on: script JSON payloads (the full structured render input), TTS audio, review-gated renders, thumbnail candidates. It does NOT hold full renders of every channel** — those stay GitHub-Release-finals + ephemeral workspace, or they fill Vercel Blob Hobby's ~1 GB TOTAL cap (hard stop, no overages) on day one. Capacity math (honest): TTS is the dominant class — a Short's audio ≈ 0.5–1 MB, so 30 channels × 1/day ≈ 15–30 MB/day ⇒ ~0.5–0.9 GB at the 30-day retention below; review-gated renders are few at launch (finance/medical lanes only). The retention days are config constants — if the cap nears at 30 channels the owner shortens TTS retention (data, not code). **Access:** `BLOB_READ_WRITE_TOKEN` as a repo secret, mirroring the `DATABASE_URL` pattern. **Failure posture:** a blob write failure records an index-only entry + one warning row and proceeds — storage failure never blocks a render (fail-open).
- **D4 — Resume is step-STATUS-based; bytes retrievability is the skip condition; re-generation is impossible by construction.** A re-dispatch with `--resume <job_id>` (workflow_dispatch input on `channel-autopilot.yml`, which already takes `channel` + `topup` inputs) creates a new job row with `resumed_from_job_id` and re-enters at the first non-succeeded step. A step is SKIPPED only when BOTH hold: (a) its `job_artifacts` row exists, AND (b) the bytes are retrievable from Blob — an index-only entry means the step RE-RUNS (renders/TTS/LLM outputs are non-deterministic; a hash alone proves nothing happened). **Stale invalidation:** the resume key includes template id+version and a brand-kit/config hash — a changed key invalidates prior artifacts and forces the re-run; an owner claim edit on the review page invalidates the script artifact. **Render input persisted before render:** hook/points/closing/thumbHeadline JSON + template version + seed + themes artifact + publishAt go to Blob (D3) and the `scripts` tables (D14) BEFORE the render step starts — so resume never re-generates a script to re-render it. Acceptance: the kill-a-worker drill (AC-P4-4).

### S2 — Upload intent + orphan reconciliation

- **D5 — NEW Neon table `upload_intents`, written BEFORE any `videos.insert`.** Columns: id, channel_id, slot_date, kind (short|doc|clip|longform), slot_idx, dedupe_key (UNIQUE — `channel_id:slot_date:kind:slot_idx`; the slot discriminator is required because kits define `slots[]` arrays — multi-slot per day is designed growth, `channel-pipeline.mjs:185`), title, status (initiated|session_open|uploaded|recorded|abandoned), session_uri (**stored as a secret — the URI is bearer-capable; never logged, never rendered in Studio**), video_id, job_id, created/updated_at. Analogy: the note you leave on the counter before carrying groceries in one trip — if you drop something, the note says what was in flight. **Cross-workflow locking decision (named):** the intent-row INSERT is the mutex — `INSERT … ON CONFLICT (dedupe_key) DO NOTHING`; zero rows inserted means another lane already claimed this slot, and the claimant either resolved it successfully or the lane marks the slot produced and skips production — a conflict NEVER results in bare proceed-to-upload. (Per-channel advisory locks were considered and rejected: the sweeper/topup and dispatch lanes share no concurrency group, so a DB-level unique index is the only lock all lanes already agree on.) Instrumented sites: `yt-daily.mjs:297`, `yt-deepdive.mjs:362`, `longvideo/shorts-clips.mjs:345`. `longvideo/longform-upload.mjs` (`RENDER_REPO = muzzamilhassan/quarry-render`, documented "emergency manual dispatch only" — `project-full-audit` line 97) keeps its artifactId ledger; it gains intents only if its render repo is verified live at implementation time — Phase 4's gating target is the three in-repo daily lanes.
- **D6 — Explicit two-step resumable upload so the session URI is ours to keep (owner-confirmed, OQ-3) — with an honesty hierarchy.** Today the googleapis client's `videos.insert` hides the resumable session URI; the research names it "the de facto idempotency token" (platform-youtube-api-oauth §4, line 209). The daily lanes switch to: POST initiate → capture `Location` header → write it on the intent row → PUT bytes → persist videoId on 201 — same quota cost as today's one-shot call. **But session URIs expire (lifetime unverified; an expired probe 404s), so the load-bearing recovery paths are deliberately the ones that never expire: the dedupe-title lookup and the nightly uploads-playlist diff (D7). The URI's real job is same-run interruption recovery** (a network blip mid-PUT), and tests mock the 404-restart so the code treats a dead URI as "fall through to title lookup", never as a failure to re-initiate blindly.
- **D7 — Orphan reconciliation, two layers.** (a) **Run-start: INSIDE `yt-daily`/`yt-deepdive` BEFORE any slot production — including `--topup` mode — the lane resolves ANY open unresolved intent for the channel (not just today's): probe session URI → on 404/expiry look the dedupe title up via `videos.list` → record or abandon. After a successful resolution the lane writes the state entry and marks the slot produced, then skips production for that slot — never bare proceed.** (b) Nightly: a reconciliation job diffs each active channel's uploads playlist against `upload_intents` + state files (`yt-mcp/state/<slug>.json` `lastVideos`) — channels.list + playlistItems.list ≈ 1–2 units/channel, never search.list. Orphans (YouTube has it, ledger didn't) are recorded with an orphan note; **the same orphan re-found on later nights updates the existing warning's last_checked, it never spawns a duplicate warning row; hand-uploads found in the playlist are recorded orphan-noted for visibility but never backfilled as intents** (they were never part of a tracked run). Ghosts (ledger has it, YouTube doesn't) are marked abandoned. This is the audit §2.3 killer: the class required BOTH a blind re-upload and no reconciliation; neither survives.
- **D8 — Scheduling semantics: deliberately minimal change, with ONE named exception.** Privacy (private + `publishAt`), thumbnails.set, pinned comment, verify-run — all continue exactly as today (AC-P4-10). Exception: **on a resumed or late upload, publishAt is RECOMPUTED from the kit's slot times** — a stale publishAt in the past means instant publish (API research ground truth), which a review delay must never cause; if no future slot remains today, the lane takes the AC-P4-19 skip path.

### S3 — Warnings table + dashboard

- **D9 — NEW Neon table `warnings`, fields per policy research §4.2.** severity (Blocking | Action-required | Warning | Advisory | Informational — the §4.1 ladder), classification, title, explanation (plain English), policy_url + policy_quote + quote_fetched_at (official sources only, never a blog), evidence (verbatim API error / field values), auto_verifiable bool, recommended_action, blocks_publishing bool, state (open | acknowledged | resolved), channel_id, job_id nullable, last_checked_at, acknowledged_by/at, resolved_by/resolve_note (manual resolves are audited, never silent), resolved_at. **Emitter→severity constraint:** only emitters that PROVE a publishing-path constraint — upload-path API errors, verify-run publication failure, revoked token — may write `blocks_publishing=TRUE`; job-step failures, analytics/collection failures, and everything heuristic default to Warning/Advisory. Production is never parked over an analytics read. Emitters: NEW `lib/warnings.mjs` (Node) with write-and-alert — every existing alert site also writes a row: dead channel key (`channel-pipeline.mjs:62`), quota gate (`lib/quota-ledger.mjs` path), verify-run failure (`verify-run.mjs:27`), template preflight block/warning (`channel-pipeline.mjs:140-158`), S1 job step failures, S4 gate holds/timeouts (D15/D17).
- **D10 — Hard-block list is the policy file's, verbatim (§4.3).** blocks_publishing=TRUE only for verified technical constraints: 401 revoked/expired token (`insufficientPermissions`, `youtubeSignupRequired`), 403 `quotaExceeded`, 400 `uploadLimitExceeded`, `uploadStatus=rejected`, `authenticatedUserAccountSuspended`/`channelClosed`, `longUploadsStatus=disallowed` for >15-min renders, thumbnails.set 403 when a custom thumbnail is required. **Never block on policy heuristics** — inauthentic-content risk, disclosure gaps, YPP uncertainty stay Advisory/Warning with citation. This is a developer-policy duty (don't present our judgment as YouTube's), not just a design preference.
- **D11 — Parking semantics — with the deadlock designed out.** WHILE a Blocking warning is open for a channel, the channel is parked: `channel-pipeline.mjs` checks open Blocking warnings first and skips that channel's production. **A parked run still executes the cheap auto-verifiable probes BEFORE exiting — token refresh + a 1-unit `channels.list` (quota table: channels list = 1 unit, API research line 80) — so an auto-resolvable condition can clear itself; a probe pass resolves the warning and the run proceeds normally that same day.** A nightly probe job re-tests every parked channel the same way, so an owner who fixes a token at midnight is un-parked by morning without touching anything. "Alerting once per park event" means once per park EPISODE (one alert when the channel parks; probe activity is not re-alerted per run). Other channels are unaffected. Acknowledge records "seen" (by/at) but never unblocks by itself — a revoked token is not un-revoked by acknowledging it; **the owner CAN manually resolve from /warnings (resolved_by + resolve_note recorded), which is the escape hatch for anything the probes cannot see** — non-auto-verifiable rows never auto-unpark. **(Auto-park on Blocking only, owner-confirmed OQ-6.)**
- **D12 — NEW Studio surface: `/warnings` page + `/api/warnings` (owner+staff), nav item under System (`studio/components/shell/nav.js`).** List open warnings newest-first, group by channel, severity chip, official quote + link + fetch date, evidence, last-checked, acknowledge button, **"re-check now" (runs the emitter's probe on demand) and manual resolve (owner-only, reason recorded)**, resolved history below. The existing `/api/sessions` + `/api/users` role pattern (`studio/lib/route-auth.js` `requireRole`) is the gate template.

### S4 — Review queue

- **D13 — Script contract extension: `sources[]` and `claims[]` become real.** Today's script shape is hook/points/closing only (`youtube-engine.mjs:829`); the target contract is topic-discovery research §4.1: `sources[] { id, url, title, publisher, access_date, quote_or_note }`, `claims[] { id, text, source_ids[], status: unverified|verified|conflicting|flagged }`, `disclosure { synthetic_media_required, reason, categories[] }`. Phase 4 adds these as generator output fields (prompt asks for them; validator tolerates absence for legacy templates — old shape keeps working). Claims are LLM-self-flagged with source sufficiency checks — this is triage, not fact-checking (Honest Limits). **Risk flags enrich the review UI; they do not drive gating — template membership does (D15).**
- **D14 — NEW Neon tables `scripts`, `script_sources`, `script_claims`** (master plan §2 names). Persisted at generation time, BEFORE render, linked to job_id + channel + template id + dedupe verdict id (`dedupe_verdicts` from Phase 3 — `services/ai/brain/store.py:123`; the Phase 3 spec's out-of-scope note says this table was designed for the review queue's query pattern). `script_memory` stays the embedding corpus (Phase 3 D3: the corpus of record for script TEXT); `scripts` is the record of record for review STATE. **video_id write-back owner (named): the upload sites write it** — they are the only code that holds both the returned videoId and the job_id — and the S5 win-rate join (`scripts.video_id` × snapshots) depends on that write.
- **D15 — Fail-closed gating is template-MEMBERSHIP-driven and fails closed on unreadable state.** The vocabulary of `safety.review_required` (`studio/lib/template-registry.data.js` — currently `[]` or `['finance']`) extends to `'medical'` and `'disclosure'`. **The gate asks one question: is the channel's assigned template's `review_required` list non-empty?** (assignment via `channel_template_assignments`, `studio/lib/template-registry-db.js`). Non-empty ⇒ every script for that channel holds for approval. Generator risk flags sharpen the review UI but never decide gating — a flag the generator failed to emit can never silently un-gate a finance channel. **Failure postures:** (a) IF the registry/assignment/approval state is unreadable (DB unreachable, assignment row missing for an assigned channel) THEN the slot is HELD (skipped, fail-closed) with one Action-required ntfy — except channels with NO registry assignment at all (legacy channels), which run ungated exactly as today; (b) the hold mechanism is a **last-known-assignment cache in the channel state file** (`yt-mcp/state/<slug>.json`): the cache answers gating when the DB blips, and hold-on-unreadable covers even a missing cache; (c) **registry/assignment drift** — an assignment the gate cannot resolve — writes the dedicated "review gating inactive" Action-required warning row so the condition is visible on /warnings, not just in logs. No channel names, no niche maps in code.
- **D16 — NEW Studio surface: `/review` page + `/api/review` routes (owner approves; staff read — owner-confirmed, OQ-5).** Layout per topic-discovery research §6: script text left, `sources[]` right, claim↔source links highlighted; flagged-claims panel (every non-verified claim: status + why + accept/edit/drop — an edit invalidates the script artifact per D4); the Phase 3 dedupe verdict shown as evidence; final checklist — sources verified, disclosure answered, copyright cleared. WHERE disclosure is required, the checklist presents the four official synthetic-media disclosure categories verbatim from `support.google.com/youtube/answer/14328491` (research §5.7) and approval is impossible until each is answered. **Approval→CI contract (named):** `/api/review` approve reuses the existing workflow-dispatch pattern of `studio/app/api/action/route.js` (same `GITHUB_TOKEN`/`GITHUB_PAT` env) to dispatch `channel-autopilot.yml` with `channel=<slug>&resume=<job_id>` — owner-only permission, audited. **A dispatch failure writes an Action-required warning row** — an approval can never silently become "approved but never rendered"; the owner re-triggers from the warning.
- **D17 — Approval window and timeout — defined.** A held script must be approved **before its slot's publishAt time, else by end-of-day**; enforcement is two-fold: the next run-start check (the lane refuses to produce into a still-held slot) and the nightly sweep (which also writes the timeout warning). On timeout: the slot is skipped for the day (a missing video is free — the 09-18 recycle-removal rule), the warning row records the timeout, and **the script is RETAINED awaiting_review — a later approval resumes at render (S1 resume, no re-spend) for the next computed slot (D8's publishAt recompute); no future slot today ⇒ the AC-P4-19 skip path stands.** Owner rejects → script never uploads; the slot takes the lane's existing terminal (Shorts slot skipped; doc exits for retry next doc day — same terminals Phase 3 D5 pinned).
- **D18 — Thumbnail N-candidate pick — post-upload swap, because candidates cannot precede a blocked render (ordering fixed).** Thumbnail v2 infrastructure exists (`studio/lib/thumb-templates-v2.js`, the 30-JSON template pattern, `/thumbs` pages). WHERE the admin-panel config enables picking for a channel/template (registry/kit DATA — no-static-maps respected, owner decision OQ-4), its renders produce N=3 candidates (count from template DATA), stored via the S1 artifact index. **The upload proceeds with candidate 1 set automatically — the daily queue never waits on a human. The owner picks from /review (or /videos) any time BEFORE publishAt; the pick calls `thumbnails.set` again to replace it (~50 units per swap — quota table, API research line 82). After publishAt the pick is recorded for win-rate data but not retro-applied. Unpicked = candidate 1 publishes — an explicit default, not a gap.** WHERE picking is not enabled, today's single auto-candidate continues unchanged (AC-P4-23).

### S5 — Analytics ingestion

- **D19 — NEW Neon table `analytics_snapshots`, trailing-window collection.** Columns: channel_id, date, views, engaged_views, watch_minutes, subs_delta, impressions nullable, ctr nullable, per_video jsonb (**bounded — recent/top-N window per collect, never the full catalog**), source (data_api|analytics_api), collected_at. UNIQUE(channel_id, date, source); the nightly job collects a **trailing window D-1..D-4** (Analytics numbers settle 48–72h — re-collecting recent days catches restatements) via UPSERT … ON CONFLICT — re-runs update in place, never duplicate (fixes the "one row per day" ambiguity: one row per channel+day+SOURCE). **Source semantics named:** Data API `videos.batchGetStats` (1 unit, own bucket — API research lines 72/78) returns lifetime/public counters per video; Analytics API v2 reports return per-day metrics — where both sources have the same date, **the analytics_api row wins for per-day metrics** and data_api supplies per-video view counts into both; win rates derive from the winning source only (D20). **Scope preflight:** only ~4 channels are verified to hold `yt-analytics.readonly` today; the job probes each channel's scope first — channels lacking it are SKIPPED with one Warning row (never Blocking — D9's constraint) and the owner gets a re-auth checklist (the same consent flow that added the scope on 10-03). Writer: NEW `lib/analytics-collect.mjs` + NEW `analytics-nightly.yml` workflow (pattern: `reporting-daily.yml` — 16:45 UTC slot, per-channel `YT_TOKEN_<SLUG>` secrets, token resolution via the existing `accessToken()` approach in `studio/app/api/analytics/route.js`).
- **D20 — Leaderboard + win rates read snapshots, not live calls.** `/api/analytics` (live, 1h cache) stays for the 28-day panel; NEW snapshot-backed endpoints serve: channel leaderboard (7/28/90-day windows), template win rates (join snapshots × `scripts.video_id`/`template_id` × `channel_template_assignments`), topic win rates (join via script record). Views across the network with one query — no 30-channel live-pull storm. **Expectation set:** win rates stay EMPTY until S4's scripts table has published rows, and only registry-assigned channels carry a template_id — coverage grows with Phase 5 assignment, it does not start at 100%.
- **D21 — Lag stamps are mandatory UI.** Analytics numbers settle 48–72 hours late; every snapshot-backed view displays "data through \<date\>" and never presents the trailing 2–3 days as final. Win rates exclude videos younger than 7 days (too unsettled to rank).

### S6 — Roles hardening

Client role untouched; no RLS, no tenant work (scope pivot).

### Cross-slice

- **D24 — Quota-model wiring is a Phase 4 dependency, plus the quota delta is small and named.** Today's pipeline gate (`channel-pipeline.mjs:87` `evaluate()`) runs legacy math — the 10,000-unit pool at ~1,700/upload ⇒ uploads falsely "park" after ~5/day network-wide. The Dec-2025 reality is ~100/upload from the uploads' own bucket (API research lines 72/78; `youtube_quota_models` table already exists from Phase 2 #104 — `studio/lib/quota-ledger.mjs:91`). The gate MUST consume quota-model rows when present, falling back to legacy math otherwise (AC-P4-32) — Phase 4's 30-channel scale is unbuildable on the legacy numbers. **Phase 4's own quota delta:** nightly reconciliation ≈ 1–3 units/channel (channels.list + playlistItems.list, never search.list), `batchGetStats` 1 unit (own bucket), two-step upload costs the same as today, and crash recovery AVOIDS a re-initiation (a saving). At 30 channels this rides inside the ~2,000–2,500 units/day worst case already modeled at ≈20–25% of the pool (`research/own-portfolio-30-channels-2026-10-25.md` line 54). Not a constraint.
- **D25 — Retention for every new store (bounded growth on free tiers).** Neon: `job_steps`/`job_artifacts` rows >90 days deleted; resolved `upload_intents` >30 days deleted; `analytics_snapshots` kept daily for 90 days then rolled up to weekly rows; `per_video` jsonb bounded per collect (D19). Vercel Blob: non-review bytes pruned after 30 days, resolved-intent bytes after 7 days (D3) — the prune runs in the same nightly maintenance pass as the sessions cleanup (D23) and the orphan diff (D7). Neon's ~0.5 GB free tier also hosts the Phase 3 `script_memory` corpus — the prune schedule is what keeps Phase 4 additive without a paid tier.

## Testing Decisions

- Unit: job-store schema ensure + step transitions; resume skip conditions (artifact row + bytes-retrievable; stale resume key invalidates; index-only ⇒ re-run); render-input persistence completeness (a resume finds hook/points/closing/thumbHeadline + template version + seed + themes + publishAt); intent-row lifecycle (initiated→session_open→uploaded→recorded) + INSERT-mutex conflict behavior (conflict ⇒ resolve-or-skip, never bare proceed); session-URI probe mock incl. **the 404-restart: a dead URI falls through to title lookup, never a blind re-initiate**; warnings severity/blocking classification per §4.1/§4.3 + the emitter constraint (a `quotaExceeded` string classifies Blocking; an inauthentic-content heuristic and an analytics failure NEVER do); gating truth table (membership × approval states × unreadable-state ⇒ hold); drift warning emission; snapshot UPSERT conflict semantics (analytics_api wins overlaps) + trailing-window re-collect; win-rate joins on fixtures; orphan warning idempotency (re-found orphan updates, never duplicates).
- Integration: one CI job running the pipeline against a disposable Neon branch with a fake-YouTube mode (mock `videos.insert` succeeding then the process dying before the state write); dispatch-failure path of /api/review approve (warning row written).
- Live drills: the three exit-gate drills below, executed against one pilot channel with quoted output in the QA file — each with prep and cleanup steps.

## Honest Limits

- **Analytics are late by design.** 48–72h settlement means "yesterday" is never final; win rates need ~2 weeks of snapshots before they mean anything, and they start EMPTY (S4 dependency + only registry-assigned channels carry template_id). Phase 4 ships the pipeline; the insight matures in Phase 5/6.
- **Analytics scope coverage is partial at launch.** Only ~4 channels are verified to hold `yt-analytics.readonly`; the rest skip with a Warning until the owner re-auths them (D19 checklist). Leaderboards cover the re-authed set, not all 30, until then.
- **No historical backfill.** Snapshots start the first night they run. There is no replaying 2025 — the Analytics API only serves what YouTube still serves.
- **The review queue triages; it does not fact-check.** Claim statuses are generator-self-flagged + source-sufficiency heuristics. No external fact-check API (topic-discovery research §5 defers Copyleaks et al.). The owner's eyes remain the real gate.
- **Blob is scoped and finite; DB-outage days are degraded days.** Vercel Blob Hobby is ~1 GB total with a hard stop — the scoped byte classes + prune keep it inside, monitored by the nightly pass. IF Neon is unreachable, the pipeline continues log-only (AC-P4-5): **no job/intent/warning rows are written that day (accepted degradation), ntfy alerts still fire (the fallback channel), and resume state is absent — so a failure that day can re-spend research/script/TTS.** Session URIs expire (lifetime unverified) — recovery leans on title lookup + playlist diff, not the URI (D6).
- **Resume is step-granular, not byte-granular.** A killed render re-renders from its persisted input; a half-finished file is never resumed mid-file. Steps whose bytes were pruned or never blobbed re-run — the index proves what happened, not that bytes survive forever.
- **ntfy stays.** The dashboard is the record; the phone push stays the bell. Nothing in Phase 4 replaces ntfy.
- **Client role stays dormant.** No tenant surfaces, no RLS, no client-facing review UI.
- **Warnings are pipeline-verifiable facts only.** Strike counts, monetization status, inauthentic-content review outcomes are Studio/email-only on YouTube's side (policy research §3.1) — the dashboard will never show them and must not pretend to.
- **Longform lane liveness unverified.** `longvideo/longform-upload.mjs` depends on the external `muzzamilhassan/quarry-render` repo (documented emergency-manual-only); Phase 4 instruments the three in-repo lanes and treats longform as legacy until verified live at implementation (D5).
- **Daily Excel stays.** `daily-excel-report.mjs` + git-committed stats continue unchanged; snapshots supplement, not replace (AC-P4-28).

## Out of Scope

Cloud Run render migration, composites archive consolidation + `asset_registry` (Phase 6); 30+ catalog authoring (Phase 5); search-bucket discipline automation (Phase 6); corpus chat UI; multi-tenant anything; YouTube quota-audit application; SaaS billing/plans; auto-approve of low-risk scripts ("tenant opt-in auto-schedule" from the research — an owner decision for a later phase); a per-step append-only `job_events` log (divergence flagged in D1 — additive later if the owner wants it).

## Acceptance Criteria (EARS)

### S1 — State machine + artifacts

- AC-P4-1: WHEN a channel pipeline run starts, the system shall create one `jobs` row and one `job_steps` row per planned step, with channel, kind, trigger, and started_at; steps disabled by config (e.g. the PLATFORMS_PAUSED lanes) shall be recorded as skipped.
- AC-P4-2: WHEN a step finishes (any outcome), the system shall update that step's status (succeeded|failed|skipped) and, for produced files, write one `job_artifacts` row with the content hash and location — the same file re-produced later yields the SAME hash and no duplicate artifact row.
- AC-P4-3: WHEN a step fails, the job row shall record failed-at-step and the pipeline SHALL CONTINUE TO run the remaining independent steps; exit semantics shall stay exactly as today — end-of-run exit 0, unknown slug and preflight-block exit 1.
- AC-P4-4: WHEN a job is re-dispatched with `--resume`, the system shall skip a step ONLY when its artifact row exists AND its bytes are retrievable from Blob; WHEN the resume key (template id+version + brand-kit/config hash) no longer matches, or the bytes are missing, the step shall re-run; the persisted render input (hook/points/closing/thumbHeadline + template version + seed + themes + publishAt) means a killed render NEVER re-generates its script or TTS.
- AC-P4-5: IF the Neon connection is unavailable, THEN the pipeline SHALL CONTINUE TO run exactly as today (log-only, no job rows) with one warning — a dead database can never darken production; that day's runs shall have no job/intent/warning records and no resume state (accepted degradation, named in Honest Limits).

### S2 — Upload intents + orphans

- AC-P4-6: WHEN any upload lane is about to upload, the system shall first persist one `upload_intents` row keyed UNIQUE per channel+slot_date+kind+slot_idx; IF the insert conflicts (another lane claimed the slot), THEN the lane shall resolve the existing intent or mark the slot produced and skip — a conflict never proceeds to a second upload.
- AC-P4-7: WHEN the resumable upload session opens, the system shall persist the session URI on the intent row BEFORE the first byte is sent, stored as a secret (never logged, never rendered), and shall persist the returned videoId on the same row when the upload is accepted.
- AC-P4-8: WHEN a lane starts (including `--topup` mode), it shall resolve ANY open unresolved intent for the channel BEFORE slot production — probing the session URI, falling through to a dedupe-title lookup on expiry/404 — and after a successful resolution shall write the state entry, mark the slot produced, and skip production for that slot, WITHOUT uploading again.
- AC-P4-9: WHEN the nightly reconciliation runs, the system shall diff each active channel's uploads playlist against intents + state (channels.list + playlistItems.list only): orphans recorded with an orphan note, ghosts abandoned; re-finding a known orphan shall update the existing warning's last_checked, never create a new row; hand-uploads shall be recorded orphan-noted and never backfilled as intents.
- AC-P4-10: WHEN uploads succeed normally, the system SHALL CONTINUE TO behave exactly as today — private upload, thumbnail set, pinned comment, verify-run proof, state writes — EXCEPT that a resumed or late upload recomputes publishAt from the kit's slot times (a past publishAt would publish instantly); no future slot today takes the AC-P4-19 path.

### S3 — Warnings

- AC-P4-11: WHEN any existing alert site fires (dead channel key, quota budget reached, verify-run failure, template preflight block, failed job step, gate hold/timeout), the system shall write one `warnings` row (severity, evidence, policy citation where one exists) AND send the existing ntfy alert — the push never disappears.
- AC-P4-12: WHEN a condition on the policy §4.3 hard-block list is detected, the system shall set blocks_publishing=TRUE; no other emitter (job-step failure, analytics/collection failure, policy heuristic) shall ever write blocks_publishing=TRUE.
- AC-P4-13: WHILE a Blocking warning is open for a channel, the system shall skip that channel's production (parked) BUT shall first run the cheap auto-verifiable probes (token refresh + 1-unit channels.list) so a self-healing condition can clear; alerting happens once per park EPISODE, not per run; other channels run unaffected.
- AC-P4-14: WHEN a probe passes for an auto-verifiable warning — from a parked run or the nightly probe job that re-tests every parked channel — the system shall resolve the warning automatically and the channel resumes (same day for a probe passed at run-start).
- AC-P4-15: WHEN the owner manually resolves a warning, the system shall record resolved_by and a resolve note; non-auto-verifiable Blocking rows shall never auto-unpark — only a passing probe or the owner's manual resolve clears them.
- AC-P4-16: WHEN the owner opens /warnings, the system shall list open warnings grouped by channel with severity, official quote + source link + fetch date, evidence, last-checked, plus "re-check now" and (owner-only) manual resolve; IF there are none, THEN an explicit empty state.

### S4 — Review queue

- AC-P4-17: WHEN a script is generated, the system shall persist it (text, sources[], claims[], disclosure flags, template, job) and the full structured render input BEFORE any render starts.
- AC-P4-18: WHEN the channel's assigned template has a non-empty `review_required` (template membership — generator risk flags enrich the UI but never gate), the system shall hold each script at awaiting_review and SHALL NOT render, upload, or schedule it until an approval row exists; IF the registry/assignment/approval state is unreadable, THEN the slot shall be held (fail-closed) with one Action-required ntfy and a "review gating inactive" warning row — while channels with no registry assignment at all SHALL CONTINUE TO run ungated as today.
- AC-P4-19: IF a held script is not approved before its slot's publishAt (else end-of-day), THEN the run-start check and nightly sweep shall skip the slot for that day, record one Action-required timeout warning, and RETAIN the script awaiting_review — a later approval resumes at render without re-spend (no future slot today means it waits for the next).
- AC-P4-20: WHEN the reviewer opens a script, the system shall show script text and sources side-by-side with claim↔source links, a flagged-claims panel (every non-verified claim), and the Phase 3 dedupe verdict where one exists; an owner claim edit shall invalidate the script's artifact (D4 stale rule).
- AC-P4-21: WHERE disclosure is required, the system SHALL require every item of the four-category synthetic-media checklist (official wording, `support.google.com/youtube/answer/14328491`) to be answered before approval is possible.
- AC-P4-22: WHEN the owner approves, the system shall dispatch `channel-autopilot.yml` (channel + resume=job_id) via the existing /api/action workflow-dispatch pattern, owner-only; IF the dispatch fails, THEN an Action-required warning shall record it (never a silent approved-but-not-rendered); WHEN the owner rejects, the script never uploads and the slot takes the lane's existing terminal.
- AC-P4-23: WHERE picking is enabled for the channel/template, the render shall produce 3 thumbnail candidates (template-data count) and the upload shall proceed with candidate 1 set; WHEN the owner picks before publishAt, the system shall swap the thumbnail via `thumbnails.set`; after publishAt the pick shall be recorded but not applied; WHERE picking is not enabled, the system SHALL CONTINUE TO auto-use today's single candidate with zero interaction.

### S5 — Analytics

- AC-P4-24: WHEN the nightly analytics job runs, it shall probe each channel for `yt-analytics.readonly`, collect a trailing window (D-1..D-4) into `analytics_snapshots` UNIQUE per channel+date+source via UPSERT (re-runs update in place, never duplicate), with analytics_api winning overlapping dates for per-day metrics and data_api supplying per-video public counters; IF a channel lacks the scope, THEN it shall be skipped with one Warning row (never Blocking) and listed on the owner's re-auth checklist.
- AC-P4-25: WHEN any snapshot-backed view renders, the system shall display "data through \<date\>" and exclude the trailing unsettled window (48–72h) from rankings; win rates exclude videos younger than 7 days.
- AC-P4-26: WHEN the owner opens the leaderboard, the system shall rank channels over a selectable window (7/28/90 days) from snapshots with zero live API calls.
- AC-P4-27: WHEN a published video has a template assignment, its snapshot performance shall roll into per-template and per-topic win rates visible in Studio; win rates shall start empty and cover only registry-assigned channels (expectation, D20).
- AC-P4-28: The system SHALL CONTINUE TO produce the Daily Excel report, commit `state/`+`logs/` history, and serve the live 28-day /api/analytics panel exactly as today.

### S6 — Sessions

- AC-P4-29: WHEN the owner revokes another user's session from the admin view, that user's next request shall be unauthenticated (redirect to login) — instant, not at cookie expiry.
- AC-P4-30: WHEN the cleanup pass runs, the system shall delete sessions that are expired or revoked for more than 30 days.
- AC-P4-31: The system SHALL CONTINUE TO support self-service device list + sign-out-everywhere and the proxy route→role matrix unchanged.

### Cross-slice

- AC-P4-32: WHEN the pipeline evaluates the daily quota budget, it shall consume `youtube_quota_models` rows (Phase 2 #104) when present for the project; IF no quota-model row exists, THEN it falls back to today's legacy math — the ~5-upload/day false park must not bound Phase 4 scale.
- AC-P4-33: WHEN the nightly maintenance pass runs, it shall prune per D25: job_steps/job_artifacts rows >90 days, resolved upload_intents >30 days, Blob bytes past their class retention (non-review >30 days, resolved-intent >7 days), and analytics_snapshots older than 90 days rolled up to weekly — table and bucket growth stay bounded on the free tiers.

### Exit-gate drills (master plan line 158 — each executable, with prep and cleanup, evidence quoted in the QA file)

- AC-P4-Drill-1 (kill-a-worker): cancel a pilot channel's job during the render step; re-dispatch with `--resume`; PASS = the run re-enters at render with script+TTS steps skipped from persisted bytes (scoped Blob), no second research/script/TTS spend, parent/child job rows linked. Cleanup: delete the drill upload, close the drill job rows.
- AC-P4-Drill-2 (revoked token): back up a test channel's token secret; simulate 401 `insufficientPermissions`; PASS = one Blocking warning with the verbatim error, the channel parks, the parked run's probe still executes, replacing the token leads to auto-resolve via probe/nightly job and the channel un-parks. Cleanup: restore the original secret, resolve any residual warning rows.
- AC-P4-Drill-3 (medical claim): PREP — author a disposable test template with `review_required: ['medical']` (registry data only), assign it to the pilot channel; run a generation whose fixture claim is unverified; PASS = the script holds in the review queue, no render/upload/schedule occurs, approval dispatches the resume run, a rejection leaves the video never-uploaded. Cleanup: unassign and retire the test template, delete drill script/upload rows.
