# BYOK (Bring Your Own Key) — Free-Tier Limits, Capacity Math, SaaS Patterns, Security Checklist

Research date: 2026-10-09. Scope: Quarry Studio BYOK design — each channel owner adds their own API keys via the dashboard; pipeline uses the channel's keys first, falls back to shared keys. Stack: Next.js 16 on Vercel + Neon Postgres + GitHub Actions + libsodium already in the codebase.

Method: primary sources (official rate-limit/pricing/security docs) fetched directly; where a provider no longer publishes a table (Google, Groq free plan), the last archived official table or corroborating secondary sources are used and marked. All estimates are explicitly marked **[estimate]**.

## 2. CAPACITY MATH — why one shared key stops scaling, and BYOK is per-channel

### Assumptions per channel (all **[estimate]**, based on Quarry's output spec: 1 documentary/week of 8–12 min + 7 Shorts/week)

| Task | LLM calls/week | Tokens in+out/week (est.) |
|---|---|---|
| Documentary: topic research + angle (2), outline (1), script draft (1), revise/polish (2), title/desc/tags (1), chapters/captions (1), stock-media clip queries for ~30 scenes batched (3) | ~11 | ~70K (research-heavy inputs: 5–10K/call; script 12K in / 5K out) |
| Shorts ×7: per short topic+hook+script (2), captions/hashtags (1), clip queries batched (1–2) | ~30 (4–5 each) | ~35K (5K each) |
| Chain retries / provider failover overhead (~30%) | ~12 | ~30K |
| **Total per channel** | **~53 calls/week ≈ 8 calls/day** | **~135K tokens/week ≈ 20K tokens/day** |

Round planning figure: **~8 calls/day and ~20K tokens/day per channel** (this is deliberately padded; a lazy channel is half this, an aggressive one 2x).

### How many channels ONE free key supports

| Provider (free key) | Daily budget | Calls-bound capacity | Tokens-bound capacity | Binding limit |
|---|---|---|---|---|
| Gemini 2.5 Flash | 250 RPD | 250 ÷ 8 ≈ **31 channels** | 250K TPM never binds at this scale | RPD ≈ 31 ch |
| Gemini 2.5 Flash-Lite | 1,000 RPD | 1,000 ÷ 8 ≈ **125 channels** | — | RPD ≈ 125 ch |
| Groq llama-3.3-70b | 1K RPD, **100K TPD** | 1,000 ÷ 8 = 125 ch | 100,000 ÷ 20,000 = **5 channels** | TPD ≈ 5 ch |
| Groq gpt-oss-120b | 1K RPD, 200K TPD | 125 ch | 200,000 ÷ 20,000 = **10 channels** | TPD ≈ 10 ch |
| Cerebras gpt-oss-120b | 1M TPD | 1,000,000 ÷ 20,000 = 50 ch | ~50 channels | **5 RPM** burst (parallel clip-query batches will 429 without client-side spacing) |
| Mistral Experiment | ~1B tokens/mo ≈ 33M/day [estimate] | hundreds | 33M ÷ 20K ≈ 1,600 ch | 1 RPS burst + training opt-in caveat |
| HuggingFace free | $0 credits | 0 | 0 (pay-per-use only, or $2/mo PRO credits ≈ 100K cheap-model tokens) | — |

### The shared-key failure case (why BYOK, in two lines of arithmetic)

- **20 client channels on the owner's ONE Gemini key:** 20 × 8 = 160 calls/day. Under the 250 RPD cap, but the owner's whole personal quota is gone, and the 10 RPM ceiling is shared across all concurrent builds — two channels rendering simultaneously with parallel clip queries starts producing 429s. **At 40 channels: 320 > 250 RPD — hard failure.** And the quota is per *project*, so adding more keys from the same owner project adds nothing ([Google rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)).
- **5 channels on ONE Groq key:** 5 × 20K = 100K tokens = the entire llama-3.3-70b daily allowance on day one; **10 channels need 200K TPD = the gpt-oss-120b cap exactly** ([Groq rate limits](https://console.groq.com/docs/rate-limits), [archived llama-3.3-70b row](https://web.archive.org/web/20250901000000/https://console.groq.com/docs/rate-limits)). The token budget, not the request budget, is what Groq-rations.
- **Media keys:** Pexels 20,000/month ÷ ~400 search calls/month/channel ≈ 50 channels, but the 200/hour cap is shared across concurrent builds ([Pexels Help](https://help.pexels.com)); Pixabay's 100/60s is fine but the "no automated mass queries" clause means the owner's key absorbs everyone's abuse risk ([Pixabay docs](https://pixabay.com/api/docs/)).

**Conclusion:** one shared key set caps the business at ~5 channels (Groq-bound), makes every client's traffic the owner's legal/abuse exposure, and creates a single 429 point of failure. BYOK per channel multiplies capacity linearly with clients (each key = its own project/org quota), keeps each client's usage on their own account, and matches what the providers' own anti-circumvention policies expect (one key per person, not one person with many keys).

## 3. BYOK PATTERNS IN SAAS

### 3.1 Encryption at rest

- **Envelope encryption is the standard:** encrypt each secret with a data key, wrap the data key with a master/key-encryption key, and **never store the KEK next to the ciphertext** ("you should not store keys next to the secrets they encrypt"); use authenticated encryption — **AES-256-GCM or ChaCha20-Poly1305** (both available in libsodium) ([OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). Concretely for Quarry: one master secret in a Vercel encrypted env var, per-key random nonce, `crypto_secretbox`/AEAD via the already-present libsodium, ciphertext + nonce + version in Neon; Neon encrypts data at rest itself, but that only protects against disk theft — it does not replace app-level envelope encryption because the app (and any DB reader) can always read plaintext ([Vercel: env vars are encrypted at rest](https://vercel.com/docs/environment-variables); Neon's own security posture covers at-rest encryption at the platform layer).
- **Real implementations to copy:**
  - **LibreChat**: user-supplied keys (`apiKey: "user_provided"`) encrypted at rest with AES-256-CBC driven by `CREDS_KEY`/`CREDS_IV` env vars; admin-configured endpoints return only an `apiKeyPreview`, never the key ([LibreChat custom endpoint docs](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/custom_endpoint)). Cautionary tale: **CVE-2026-32625** — an MCP-server URL injection leaked `CREDS_KEY`/`CREDS_IV`/`JWT_SECRET` to attacker servers, which would allow decrypting every stored third-party key; the lesson is that the master secret is the crown jewel and any place it surfaces (config endpoints, logs, debug UIs) is an exfil vector ([SentinelOne disclosure via search; NVD CVE-2026-32625](https://nvd.nist.gov/vuln/detail/CVE-2026-32625)).
  - **Dify**: provider credentials encrypted with a **hybrid RSA/AES scheme — tokens encrypted with a tenant-specific RSA public key** (per-workspace keys, so one tenant's leak doesn't cross tenants) ([Dify GitHub issue #2230](https://github.com/langgenius/dify/issues/2230), [Dify docs](https://docs.dify.ai)).
  - **n8n**: credentials encrypted with a per-instance key (`N8N_ENCRYPTION_KEY`); GitGuardian's analysis notes that DB dump + key file = offline decryption of everything, so the key must live separately from backups ([n8n community](https://community.n8n.io), [GitGuardian blog](https://blog.gitguardian.com)).
  - **OpenRouter**: states provider keys are "securely encrypted" and **read-back responses mask the key as a short label like `sk-...AbCd`** ([OpenRouter BYOK docs](https://openrouter.ai/docs/use-cases/byok)).
  - **Vercel's own convention** (a good UX bar to match): Config vs **Secret** types, where "Secret values are write-only after saving" ([Vercel env vars docs](https://vercel.com/docs/environment-variables), [sensitive env vars](https://vercel.com/docs/environment-variables/sensitive-environment-variables)).

### 3.2 UI conventions

- **Masked display after save** — never render the full key again: OpenRouter returns `sk-...AbCd` style labels ([BYOK docs](https://openrouter.ai/docs/use-cases/byok)); LibreChat returns `apiKeyPreview` ([docs](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/custom_endpoint)); Vercel Secrets are write-only post-save ([docs](https://vercel.com/docs/environment-variables)); GitHub Actions secrets return only metadata (`name`, `created_at`, `updated_at`), never the value ([GitHub REST docs](https://docs.github.com/en/rest/actions/secrets)).
- **Validate before save ("Test key" button)** — make one cheap live call per provider (e.g., 1-token Gemini/Groq/Cerebras chat completion, 1 Pixabay/Pexels search) and show the model/plan/quota returned; Google's key-type shift (unrestricted keys rejected since 2026, auth keys default May 28, 2026) makes server-side validation mandatory rather than optional, because a key can paste fine and still fail every call ([Google key docs](https://ai.google.dev/gemini-api/docs/api-key)).
- **Per-provider status row**: name, provider, masked key, last-validated timestamp, last error (401/403/429), and an explicit "channel key first → shared fallback" indicator — OpenRouter's **Prioritized vs Fallback** key sections are the exact UX for "use this channel's key, then shared" ([OpenRouter BYOK docs](https://openrouter.ai/docs/use-cases/byok)).
- **Revoke/rotate**: replace-then-disable rotation is the provider-recommended dance (Google: generate replacement, deploy, *then* disable the old key to avoid downtime, and audit usage logs) ([Google key safety doc](https://ai.google.dev/gemini-api/docs/api-key)); same for OpenAI (new key → revoke old) ([howtorotate.com/OpenAI procedure](https://howtorotate.com)). In the dashboard, "replace" should be a single flow that overwrites ciphertext and bumps the key version.
- **Precedents that do BYOK**: OpenRouter (full-featured: per-key model filters, member filters, `allowed_api_key_hashes` SHA-256 allowlists, BYOK management REST API) ([docs](https://openrouter.ai/docs/use-cases/byok)); HuggingFace "Custom Provider Key" (HF swaps auth server-side; billing flips to the provider) ([HF pricing](https://huggingface.co/docs/inference-providers/pricing)); LibreChat per-user credentials; Dify per-tenant credentials; n8n instance-level credentials. AnythingLLM is the counter-example: keys are global admin settings, and per-workspace credentials remain a requested feature (issue #1440) — i.e., per-channel BYOK is a genuine differentiator ([AnythingLLM issue #1440](https://github.com/Mintplex-Labs/anything-llm/issues/1440)). Zapier-style apps typically avoid BYOK for LLMs entirely (they bill usage), which is the alternative path if BYOK UX becomes a support burden.

### 3.3 GitHub Actions — getting per-channel keys into the pipeline at runtime

Three viable patterns, ranked for Quarry (Vercel + Neon already in place):

1. **Runtime fetch from the platform API (recommended).** The workflow holds ONE platform credential (a pipeline token in repo secrets); a step calls e.g. `POST https://quarry-studio.../api/pipeline/keys {channelId}` which authenticates the token, decrypts that channel's keys in memory (vercel function + libsodium + Neon), and returns them as job-scoped output/masked env. Pros: keys never live in GitHub; revocation is instant (disable in dashboard, next run fails over to shared); full audit trail in your own DB; no per-tenant GitHub churn; works for unlimited channels. Cons: dashboard must be reachable from Actions (it is — it's a Vercel deployment); a leak of the pipeline token leaks *retrieval rights*, so make it a scoped, rotatable token and mask every value with `::add-mask::`. This mirrors what HF/OpenRouter do internally (router holds keys, clients hold one credential) ([HF custom key model](https://huggingface.co/docs/inference-providers/pricing), [OpenRouter BYOK](https://openrouter.ai/docs/use-cases/byok)).
2. **Per-tenant GitHub secrets written via API.** `PUT /repos/{owner}/{repo}/actions/secrets/{name}` with the value **encrypted using libsodium sealed box against the repo public key**; classic tokens need the `repo` scope, fine-grained tokens need the Secrets repository permission (write); **secrets are write-only — never readable back** ([GitHub REST Actions secrets](https://docs.github.com/en/rest/actions/secrets)). Pros: native CI secrecy, automatic log masking, no runtime dependency. Cons: doesn't scale with tenants — a secret per channel×provider (40 channels × 6 providers = 240 writes on every rotation), secret-size cap 48 KB and per-repo/environment secret count caps are low hundreds-to-1,000 ([GitHub secrets docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions), counts partially from [community/limits guides — treat exact counts as unverified](https://github.com/orgs/community/discussions)); rotation automation needs a long-lived PAT with `repo` scope — itself a crown-jewel credential; and there's zero usage audit beyond GitHub's metadata. Note the task brief's "secrets:write needs admin PAT": repo secrets need collaborator write + `repo` scope; *org-level* secret endpoints need `admin:org` ([GitHub secrets docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)).
3. **Encrypted files committed per channel (repo-stored ciphertext).** Each channel's keys libsodium-boxed to the CI public key, committed as `keys/<channel>.age`; CI holds the identity. Pros: no network dependency. Cons: ciphertext and its history live in git forever (rotation can't scrub history), revocation requires a commit + workflow file changes, and GitHub explicitly warns its own workaround for big secrets "does not redact secrets printed in logs" — same risk class applies ([GitHub secrets docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)). OWASP warns against repo/fork leakage of secrets outright ([OWASP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). Acceptable only as an offline/backup mode, not the primary path.

## 4. SECURITY REQUIREMENTS CHECKLIST (storing third-party keys server-side)

Providers' own "keep your key safe" guidance to anchor the policy: Google — treat the key "like a password," never check into Git, never ship in client code, backend proxy for clients, env vars or a secret manager in production ([Gemini API key safety](https://ai.google.dev/gemini-api/docs/api-key)). OpenAI — never deploy keys in client-side environments (browsers/mobile), server-side + env vars + secret manager only, revoke immediately on exposure ([Best Practices for API Key Safety](https://help.openai.com/en/articles/5112594-best-practices-for-api-key-safety), [rotation procedure](https://howtorotate.com)). OWASP — the canonical checklist ([cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).

1. **Encrypt at rest with envelope encryption.** Random per-key nonce, AEAD (XChaCha20-Poly1305 / AES-256-GCM via libsodium), data-encryption keys wrapped by a master secret held only as a Vercel encrypted env var; never store the master next to the ciphertext; keep a `key_version` column for rotation ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). Neon's platform at-rest encryption is defense-in-depth, not a substitute ([Vercel env vars](https://vercel.com/docs/environment-variables)).
2. **Never log keys.** Mask in every logger, never print provider request headers, add the key value to the redact list at creation time; "secrets should never be logged" and pipeline output must not reveal them ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)); GitHub's docs warn that values decrypted in-workflow are NOT auto-redacted if you print them ([GitHub secrets docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)).
3. **Never return the full key to the client after save.** Write-only semantics + `sk-...last4` preview only, exactly like Vercel Secrets, OpenRouter, LibreChat's `apiKeyPreview`, and GitHub's metadata-only API ([Vercel](https://vercel.com/docs/environment-variables), [OpenRouter](https://openrouter.ai/docs/use-cases/byok), [LibreChat](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/custom_endpoint), [GitHub REST](https://docs.github.com/en/rest/actions/secrets)).
4. **Validate on save, and rate-limit the validation endpoint.** One cheap live call per provider; surface provider-plan/quota info; Google's 2026 auth-key/unrestricted-key changes mean some keys validate-but-fail at call time, so also validate lazily on first real use ([Google key docs](https://ai.google.dev/gemini-api/docs/api-key)). Rate-limit/authorize `/validate` per user and per IP because it triggers outbound provider calls on your infrastructure (abuse-amplification vector) ([OWASP access-control/logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).
5. **Audit trail of key changes.** Append-only log: who set/rotated/deleted which channel key, when, from which IP, plus validation results — tamper-resistant timestamps, ≥90 days retention ([OWASP logging section](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).
6. **Scoped role checks.** Only the channel owner (or platform admin) may read/write that channel's keys; least-privilege, per-secret authorization; your pipeline token's DB role should select decrypted keys only for the channel being processed ([OWASP access control](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).
7. **Rotation support.** Store versioned ciphertext so old blobs stay decryptable during a master-secret rotation; UI "replace key" overwrites + bumps version; Google's dance: add new → verify → disable old → audit usage ([Google key safety](https://ai.google.dev/gemini-api/docs/api-key)); note OWASP/NIST: user-chosen secrets need rotation mainly on evidence of compromise — don't force monthly client-key churn ([OWASP rotation section](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).
8. **Handle provider-side revocation/invalid keys.** Treat 401/403 from a provider as "key dead": mark the key `invalid` in the dashboard, notify the channel owner (ntfy: 250 free msgs/day is plenty ([ntfy docs](https://docs.ntfy.sh/publish/))), and transparently fall back to the shared key while flagging the run — OpenRouter's Prioritized→Fallback routing is the model ([OpenRouter BYOK](https://openrouter.ai/docs/use-cases/byok)); Google's compromise playbook (replace, deploy, disable, audit) applies when the leak is on your side ([Google key docs](https://ai.google.dev/gemini-api/docs/api-key)).
9. **Minimize plaintext residency.** Decrypt at the last possible moment in the Vercel function, hold in memory only for the call, never write decrypted keys to `/tmp`, disk, or workflow artifacts; prefer passing them as masked env/outputs over files ([OWASP memory + CI/CD sections](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).
10. **Protect the master secret like LibreChat's post-CVE world.** The 2026 LibreChat CVE showed master-secret exfil = total key compromise; restrict any debug/config surface that can reflect env vars, and consider a KMS/HSM-backed master later if this becomes multi-tenant paid SaaS at scale ([CVE-2026-32625](https://nvd.nist.gov/vuln/detail/CVE-2026-32625), [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)).
